# Pilot

Write this before the first draft or send.

```text
Pilot: <name>                         Owner: <person>    Decision date: <date>
Hypothesis:     If we <change>, <metric> moves from <baseline> to <target>.
One variable:   <the only change>
Scope:          <people or accounts>, <segment>, <channel>
Duration:       <read window>
Success:        <metric at or above the bar> -> scale one cap or one scope
Revise:         <metric inside the band> -> change one variable and rerun
Kill:           <literal reversal> -> stop and record why
Guardrails:     sender health, suppression, previewed credit ceiling
Guardrail stop: <bounce, opt-out, or cost condition that stops even a good leading metric>
Kill switch:    <person>, and the skill that pauses or stops
Read with:      <capability ids>
Check-in:       <date>
```

Read windows are estimates, not promises. Cold email or LinkedIn: 14 days after the first send. New sending domains: 14 confirmed warm-up days before volume. A set of plays: 30 days. Founder posting: several weeks, judged by who reaches out. At small volume, prefer a large-effect kill line (zero positive replies after the agreed sends on copy the user would send) over a tiny rate gap.

The leading metric is the closest one to revenue that the window can show. Every kill line names its read. Compare the workspace with its own history before any outside panel.

Verdict line: SCALE, REVISE, or KILL, the number that decided it, and the single next action.

## Where it lives

| Artifact | Where |
| --- | --- |
| Snapshot and constraint | Conversation, then a Context page through [`knowledge`] |
| Agreed problem | Context decision with the kill line as the reversal condition |
| Motion and options | One Context page for the motion |
| Verdict | The same decision log |

A later session starts with `workspace.observability.approvals_list`, the decision page, and the pilot's due reads. Then one sentence of status and one recommendation: continue, stop because a kill line fired, or review.

Execution stays in the skill that owns it. This skill does not enroll, send, or publish. The executing skill follows the paid-run consent rule.
